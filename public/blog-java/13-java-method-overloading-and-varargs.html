13. జావా మెథడ్ ఓవర్‌లోడింగ్ & Varargs (Compile-time Polymorphism)

☕ Java (Java 21+ LTS) 🟢 Lesson 13 of 25 📂 Part 03: Arrays, Methods & OOP (Page 3 of 5) ⏱️ 25 min read
📌 Covered in this lesson: Compile-time Polymorphism · నంబర్, టైప్ మరియు ఆర్డర్ ఆఫ్ పారామీటర్లతో ఓవర్‌లోడింగ్ · Variable-length Arguments (Type... args) వాడకం & రూల్స్

సాఫ్ట్‌వేర్ అభివృద్ధిలో ఒకే రకమైన ఆపరేషన్‌ను విభిన్న డేటా రకాలు లేదా వివిధ సంఖ్యల ఇన్‌పుట్లతో చేయాల్సి వచ్చినప్పుడు, ప్రతి ఒక్క కేస్ కోసం calculateInt(), calculateDouble(), calculateThreeNumbers() అని వందల కొద్దీ విభిన్న పేర్లు పెట్టుకుంటూ పోవడం క్లీన్ కోడ్ సూత్రాలకు విరుద్ధం. జావాలో ఒకే పేరుతో, కానీ వేర్వేరు పారామీటర్ల అమరికతో బహుళ మెథడ్లను సృష్టించే శక్తివంతమైన సదుపాయమే మెథడ్ ఓవర్‌లోడింగ్ (Method Overloading). దీనినే ఆబ్జెక్ట్-ఓరియెంటెడ్ ప్రోగ్రామింగ్ ప్రపంచంలో కంపైల్-టైమ్ పాలిమార్ఫిజం (Compile-time Polymorphism / Static Binding) అంటారు. వీటితో పాటు ఏకకాలంలో సున్నా నుండి ఎన్ని ఆర్గ్యుమెంట్లనైనా నేరుగా స్వీకరించే వెసులుబాటు కల్పించే Varargs (Variable Arguments - ...) యొక్క మెమరీ ఇంటర్నల్స్, కంపైలర్ రిసొల్యూషన్ ప్రాధాన్యతలు (Widening vs Autoboxing vs Varargs), మరియు ఆంబిగ్యుటీ ట్రాప్స్ గురించి ఈ పాఠంలో సమగ్రంగా నేర్చుకుందాం.

మల్టీ-పోర్ట్ యూనివర్సల్ ఛార్జర్ & బఫే ప్లేట్ల అనాలజీ (The Multi-Port Universal Charger & Buffet Plate Analogy):

  1. 1. Method Overloading (మల్టీ-పోర్ట్ యూనివర్సల్ ఛార్జర్ - Multi-Port Fast Charger): ఇంట్లో ఉన్న ఒక అధునాతన ఫాస్ట్ ఛార్జర్‌కు ఒకే సమయంలో USB-C, మైక్రో USB, మరియు ల్యాప్‌టాప్ పవర్ కేబుల్స్ పెట్టేందుకు 3 వేర్వేరు సాకెట్లు ఉన్నాయి. ఛార్జర్ పేరు ఒక్కటే — కానీ మీరు ఏ కేబుల్ పెడితే ఆ పరికరానికి తగిన వోల్టేజ్‌తో అది విద్యుత్తును అందిస్తుంది. అదేవిధంగా జావాలో మెథడ్ పేరు ఒక్కటే అయినప్పటికీ, మీరు పాస్ చేసే ఆర్గ్యుమెంట్ల రకం మరియు సంఖ్య ఆధారంగా జావా కంపైలర్ సరైన మెథడ్‌ను ముందుగానే బైండ్ చేస్తుంది.
  2. 2. Overloading Ambiguity (ఒకే పరిమాణం ఉన్న రెండు పోర్టుల గందరగోళం - Ambiguous Slot): ఒకే రకమైన రెండు వైర్లు వచ్చి ఏ పోర్టులోకి వెళ్లాలో స్పష్టత లేనప్పుడు ఛార్జర్ షార్ట్ సర్క్యూట్ అయినట్లుగా, జావాలో కూడా ఒక మెథడ్ కాల్ రెండు ఓవర్‌లోడెడ్ మెథడ్లకు సమానంగా సరిపోలితే కంపైలర్ కంగారుపడి reference to method is ambiguous అని ఎర్రర్ ఇస్తుంది.
  3. 3. Varargs (అన్‌లిమిటెడ్ బఫే లంచ్ ప్లేట్ - Variable Arguments Buffet Plate): ఒక విందు భోజనంలో బఫే ప్లేట్ పట్టుకుని వెళ్లినప్పుడు, మీ ప్లేట్‌లో మీరు 1 గులాబ్ జామ్ వేసుకోవచ్చు, 5 రకాల కూరలు వేసుకోవచ్చు, లేదా ఏమీ వేసుకోకుండా ఖాళీ ప్లేట్‌తో నిలబడవచ్చు (0 to N items). జావాలో Type... args అనేది ఆ బఫే ప్లేట్ లాంటిది. తెరవెనుక JVM స్వయంగా ఒక తాత్కాలిక ఎరేను (Heap Array) సృష్టించి ఎన్ని విలువలనైనా స్వీకరిస్తుంది.

ఈ పాఠం పూర్తయ్యేసరికి మీరు ఓవర్‌లోడింగ్ లోని సూక్ష్మమైన టైప్ ప్రమోషన్ నియమాలను, Varargs ఇంటర్నల్స్ మరియు ఎంటర్‌ప్రైజ్ క్లౌడ్ నోటిఫికేషన్ మల్టీ-ఛానల్ ఇంజిన్‌ను నిర్మించడంలో నిష్ణాతులవుతారు!

1. ఓవర్‌లోడింగ్ ఆవశ్యకత & కంపైల్-టైమ్ బైండింగ్ (Why Overloading Matters)

జావాలో మెథడ్ ఓవర్‌లోడింగ్ అనేది కోడ్ రీడబిలిటీని పదింతలు పెంచే అత్యద్భుతమైన ఫీచర్. ఉదాహరణకు జావా ప్రామాణిక లైబ్రరీలోని System.out.println() మెథడ్‌ను చూడండి. మీరు println(10) అన్నా, println("Hello") అన్నా, లేదా println(true) అన్నా అది సజావుగా ముద్రిస్తుంది. జావా డెవలపర్ ప్రతి డేటా రకానికి వేర్వేరు మెథడ్ పేర్లను గుర్తుపెట్టుకోవాల్సిన అవసరం లేకుండా PrintStream క్లాస్‌లో సుమారు 10 వేర్వేరు ఓవర్‌లోడెడ్ println() మెథడ్లను అందించడమే దీనికి కారణం.

కంపైల్-టైమ్ పాలిమార్ఫిజం (Static Binding): మీరు ప్రోగ్రామ్‌ను కంపైల్ (javac) చేస్తున్నప్పుడే, జావా కంపైలర్ మీరు పంపిన ఆర్గ్యుమెంట్ల డేటా టైప్‌లను పరిశీలించి, బైట్‌కోడ్‌లో ఏ నిర్దిష్ట మెథడ్‌ను ఇన్వోక్ చేయాలో ఖరారు చేస్తుంది. రన్‌టైమ్‌లో ఎటువంటి శోధన లేదా డైనమిక్ డిస్పాచ్ జరగదు కాబట్టి దీనివల్ల అప్లికేషన్ పనితీరులో ఎటువంటి నష్టం (Zero Runtime Overhead) ఉండదు.

2. ఓవర్‌లోడింగ్ 3 గోల్డెన్ నియమాలు (The 3 Golden Rules of Overloading)

ఒకే క్లాస్‌లో రెండు లేదా అంతకంటే ఎక్కువ మెథడ్లకు ఒకే పేరు ఉండాలంటే, వాటి పారామీటర్ల జాబితా (Parameter List) తప్పనిసరిగా క్రింది 3 మార్గాలలో కనీసం ఒకదానిలో భిన్నంగా ఉండాలి:

// నియమం 1: పారామీటర్ల సంఖ్యలో తేడా (Difference in Number of Parameters)
int add(int a, int b) { return a + b; }
int add(int a, int b, int c) { return a + b + c; }

// నియమం 2: పారామీటర్ల డేటా టైప్స్‌లో తేడా (Difference in Data Types)
double add(double a, double b) { return a + b; }

// నియమం 3: పారామీటర్ల వరుస క్రమంలో తేడా (Difference in Order of Types)
void printInfo(String name, int age) { ... }
void printInfo(int age, String name) { ... }

3. రిటర్న్ టైప్ & యాక్సెస్ మోడిఫైయర్ల పాత్ర (The Return Type Fallacy)

జావా బిగినర్లు అత్యంత ఎక్కువగా బోల్తా పడే ప్రమాదకరమైన అంశం ఇది:

❌ ఈ కోడ్ కంపైల్ కాదు (Compilation Error):
public class Calculator {
    public int multiply(int a, int b) { return a * b; }
    public double multiply(int a, int b) { return (double)(a * b); } // ❌ COMPILE ERROR!
}

ఎందుకు ఎర్రర్ వస్తుంది? మీరు మెథడ్‌ను కాల్ చేసేటప్పుడు కేవలం calc.multiply(10, 20); అని మాత్రమే రాస్తారు (రిటర్న్ వచ్చిన విలువను ఏ వేరియబుల్‌లోనూ స్టోర్ చేసుకోకపోవచ్చు). అప్పుడు కంపైలర్‌కు ఏ మెథడ్‌ను రన్ చేయాలో అర్థం కాదు. కాబట్టి కేవలం రిటర్న్ టైప్ లేదా యాక్సెస్ మోడిఫైయర్లను మార్చడం ద్వారా మెథడ్ ఓవర్‌లోడింగ్ సాధ్యం కాదు!

4. టైప్ ప్రమోషన్ & ఆటోమేటిక్ వైడనింగ్ రూల్స్ (Type Promotion in Overloading)

మీరు పంపించిన ఆర్గ్యుమెంట్ టైప్‌కు సరిగ్గా సరిపోయే (Exact Match) మెథడ్ లేనప్పుడు, జావా కంపైలర్ ఆటోమేటిక్‌గా చిన్న డేటా రకాలను పెద్ద డేటా రకాలుగా మారుస్తుంది (Automatic Type Promotion / Widening):

byte ➔ short ➔ int ➔ long ➔ float ➔ double
char ➔ int ➔ long ➔ float ➔ double

ఉదాహరణకు, మీరు int ఆర్గ్యుమెంట్‌ను పాస్ చేశారు, కానీ క్లాస్‌లో foo(int) లేదు. అయితే foo(long) ఉంటే, JVM ఆటోమేటిక్‌గా మీ int ను long గా ప్రమోట్ చేసి foo(long) ను విజయవంతంగా రన్ చేస్తుంది.

5. Varargs (Type... args) & హీప్ ఎరే నిర్మాణం (Variable Arguments Internals)

Java 5 కి ముందు, ఒక మెథడ్‌కు అనిశ్చిత సంఖ్యలో (Arbitrary Number) ఆర్గ్యుమెంట్లను పంపించాలంటే డెవలపర్ తప్పనిసరిగా మాన్యువల్‌గా ఒక ఎరేను సృష్టించి పంపించాల్సి వచ్చేది (ఉదా: printItems(new String[]{"A", "B"})).

దీనికి పరిష్కారంగా Varargs (Variable Arguments) ఫీచర్ ప్రవేశపెట్టబడింది. డేటా టైప్ తర్వాత మూడు చుక్కలు (Type... varName) ఉంచడం ద్వారా దీన్ని వాడతాం.

public static void logMessages(String... messages) {
    // కంపైలర్ దృష్టిలో messages అనేది సాధారణ String[] ఎరే మాత్రమే!
    for (String msg : messages) {
        System.out.println(msg);
    }
}

అంతర్గత మెకానిజం: మీరు logMessages("Err1", "Err2", "Err3"); అని కాల్ చేసినప్పుడు, జావా కంపైలర్ అంతర్గతంగా logMessages(new String[]{"Err1", "Err2", "Err3"}); గా మారుస్తుంది. మీరు సున్నా ఆర్గ్యుమెంట్లు పంపితే (logMessages()), ఖాళీ ఎరే new String[0] హీప్‌లో ఏర్పడుతుంది!

6. Varargs నియమాలు: లాస్ట్ పారామీటర్ రూల్ (The Strict Syntactic Rules)

Varargs తో పనిచేసేటప్పుడు జావా కంపైలర్ విధించిన రెండు కఠినమైన నియమాలను గుర్తుంచుకోవాలి:

  • నియమం 1 (Last Parameter Rule): మెథడ్ పారామీటర్ల జాబితాలో Varargs ఎల్లప్పుడూ చివరి పారామీటర్‌గా మాత్రమే ఉండాలి! (ఉదా: void test(int x, String... names) చెల్లుబాటు అవుతుంది; కానీ void test(String... names, int x) కంపైలేషన్ ఎర్రర్).
  • నియమం 2 (Single Varargs Rule): ఒక మెథడ్‌లో కేవలం ఒకే ఒక్క Varargs పారామీటర్ మాత్రమే ఉండాలి. ఒకే మెథడ్‌లో void test(int... a, String... b) రాయడం చట్టవిరుద్ధం.

7. Widening vs Autoboxing vs Varargs ప్రాధాన్యత (Compiler Resolution Priority)

ఒక మెథడ్ కాల్‌ను పరిష్కరించేటప్పుడు జావా కంపైలర్ అత్యంత ఖచ్చితమైన ప్రాధాన్యతా క్రమాన్ని (Resolution Hierarchy) అనుసరిస్తుంది:

కంపైలర్ రిసొల్యూషన్ 4 దశలు (Priority Order):
1. దశ 1 (Exact Match): సరిగ్గా సరిపోయే టైప్ (ఉదా: int ➔ int)
2. దశ 2 (Widening / Primitive Promotion): చిన్న ప్రిమిటివ్ పెద్ద ప్రిమిటివ్‌గా మారడం (ఉదా: int ➔ long ➔ double)
3. దశ 3 (Autoboxing / Unboxing): ప్రిమిటివ్ ర్యాపర్ ఆబ్జెక్ట్‌గా మారడం (ఉదా: int ➔ Integer)
4. దశ 4 (Varargs): వేరియబుల్ ఆర్గ్యుమెంట్లు (ఉదా: int...) — ఇది ఎల్లప్పుడూ చివరి ప్రాధాన్యత!

ముఖ్యమైన గమనిక: జావా కంపైలర్ బ్యాక్‌వర్డ్ అనుకూలత (Backward Compatibility) కోసం రూపొందించబడింది. Widening అనేది Java 1.0 నాటిది, Autoboxing మరియు Varargs అనేవి Java 5 లో వచ్చాయి. అందువల్ల పాతకాలపు Widening ఎల్లప్పుడూ Autoboxing మరియు Varargs కంటే ముందు గెలుస్తుంది!

8. Ambiguity ట్రాప్స్ & కంపైలర్ ఎర్రర్స్ (The Ambiguous Method Pitfall)

ఓవర్‌లోడింగ్ మరియు Varargs ను కలిపి వాడేటప్పుడు అత్యంత జాగ్రత్తగా ఉండాలి. క్రింది కోడ్ చూడండి:

public static void show(int... a) { System.out.println("int varargs"); }
public static void show(String... s) { System.out.println("String varargs"); }

// ఇప్పుడు మీరు ఖాళీగా కాల్ చేస్తే:
show(); // ❌ Compile Error: reference to show is ambiguous!

ఖాళీ ఆర్గ్యుమెంట్‌తో పిలిచినప్పుడు, అది int[] కావాలో లేదా String[] కావాలో కంపైలర్ తేల్చుకోలేక క్రాష్ అవుతుంది. ఇటువంటి ఆంబిగ్యుటీలను నివారించడానికి Varargs మెథడ్లను విచక్షణారహితంగా ఓవర్‌లోడ్ చేయకూడదు.

10. డెమో 2: ఫ్లెక్సిబుల్ Varargs మ్యాథ్ కాలిక్యులేటర్ (Flexible Math Calculator)

ఒకటి లేదా అంతకంటే ఎక్కువ పారామీటర్లను తప్పనిసరి చేస్తూ, మిగిలిన ఎన్ని సంఖ్యలనైనా స్వీకరించే ఫ్లెక్సిబుల్ మ్యాథ్ కాలిక్యులేటర్‌ను ఎలా డిజైన్ చేయాలో పరిశీలిద్దాం:

FlexibleVarargsCalculator.java 
public class FlexibleVarargsCalculator {

    // Overloaded sum methods
    public static int sum(int a, int b) {
        return a + b;
    }

    public static int sum(int a, int b, int c) {
        return a + b + c;
    }

    // Varargs sum for any quantity (4 or more, or dynamic collections)
    public static int sum(int... numbers) {
        int total = 0;
        for (int num : numbers) {
            total += num;
        }
        return total;
    }

    // Best Practice: At least one parameter is strictly mandatory
    public static double average(double first, double... rest) {
        double total = first;
        for (double val : rest) {
            total += val;
        }
        return total / (rest.length + 1);
    }

    public static void main(String[] args) {
        System.out.println("=================================================");
        System.out.println("🧮 FLEXIBLE OVERLOADED & VARARGS CALCULATOR");
        System.out.println("=================================================
");

        System.out.println("1. Two parameters:   sum(10, 20)             = " + sum(10, 20));
        System.out.println("2. Three parameters: sum(10, 20, 30)         = " + sum(10, 20, 30));
        System.out.println("3. Varargs (5 nums): sum(5, 10, 15, 20, 25)  = " + sum(5, 10, 15, 20, 25));
        System.out.println("4. Varargs (0 nums): sum()                   = " + sum());

        System.out.println("
5. Mandatory First Arg Average:");
        System.out.printf("   average(100.0)                     = %.2f%n", average(100.0));
        System.out.printf("   average(80.0, 90.0, 95.0, 85.0)     = %.2f%n", average(80.0, 90.0, 95.0, 85.0));

        System.out.println("=================================================");
    }
}

11. Capstone ప్రాజెక్ట్: మల్టీ-ఛానల్ క్లౌడ్ అలర్ట్ డిస్పాచర్ ఇంజిన్

ఈ అధ్యాయంలో నేర్చుకున్న అన్ని కాన్సెప్టులను (మెథడ్ ఓవర్‌లోడింగ్, Varargs, కంపైల్-టైమ్ సేఫ్టీ, స్ట్రింగ్ ఫార్మాటింగ్) సమగ్రంగా మేళవిస్తూ ఒక ఎంటర్‌ప్రైజ్ స్థాయి Multi-Channel Cloud Alert & Incident Dispatcher ను నిర్మిద్దాం:

CloudNotificationDispatcherEngine.java 
public class CloudNotificationDispatcherEngine {

    public enum Priority { LOW, MEDIUM, HIGH, CRITICAL }

    // Overloaded Dispatch Methods

    // 1. Single SMS Alert
    public static void sendAlert(String phoneNumber, String message) {
        System.out.printf("📱 [SMS DISPATCH] To: %s | Message: %s%n", phoneNumber, message);
    }

    // 2. Email with Subject and Priority
    public static void sendAlert(String email, String subject, Priority priority, String message) {
        System.out.printf("📧 [EMAIL DISPATCH] To: %-18s | Priority: %-8s | Subj: %-15s | Body: %s%n",
                email, priority, subject, message);
    }

    // 3. Multi-Channel Broadcast via Varargs
    public static void sendAlert(Priority priority, String message, String... targetChannels) {
        System.out.printf("%n📢 [BROADCAST ALERT - %s] Message: '%s'%n", priority, message);
        System.out.println("   Active Target Nodes (" + targetChannels.length + "):");
        for (String channel : targetChannels) {
            System.out.println("    └─► Dispatched to channel: " + channel);
        }
    }

    public static void main(String[] args) {
        System.out.println("=================================================");
        System.out.println("🚨 ENTERPRISE CLOUD MULTI-CHANNEL DISPATCHER");
        System.out.println("=================================================
");

        // Use case 1: Quick SMS
        sendAlert("+91-9848012345", "OTP for login: 928410. Valid for 5 mins.");

        // Use case 2: Rich Email
        sendAlert("balaji@company.com", "DB High Memory", Priority.HIGH, "PostgreSQL RAM exceeded 88% threshold.");

        // Use case 3: Varargs Incident Broadcast to multiple internal channels
        sendAlert(
            Priority.CRITICAL,
            "Service Outage: PaymentGateway-v2 returned 503 Service Unavailable",
            "#slack-incident-war-room",
            "pagerduty:on-call-dev",
            "webhook:https://status.company.com/api/v1/update",
            "email:executives@company.com"
        );

        System.out.println("
=================================================");
        System.out.println("✅ All notification streams dispatched successfully!");
        System.out.println("=================================================");
    }
}

12. ప్రొడక్షన్ పిట్‌ఫాల్స్, బెస్ట్ ప్రాక్టీసెస్ & 5 క్విజ్‌లు (Best Practices & Quizzes)

🚫 ప్రొడక్షన్‌లో నివారించాల్సిన 4 ఘోరమైన తప్పులు (Production Pitfalls):

  1. కేవలం రిటర్న్ టైప్ మార్చి ఓవర్‌లోడ్ చేయాలని ప్రయత్నించడం: ఇది కంపైలేషన్ ఎర్రర్‌కు దారితీస్తుంది.
  2. ప్రాచీనమైన Widening మరియు Autoboxing ను ఒకేసారి ఆశించడం: జావా int ను ఒకే స్టెప్‌లో Long (Widening + Autoboxing) గా మార్చదు! int ➔ long సాధ్యమే, లేదా int ➔ Integer సాధ్యమే, కానీ int ➔ Long కంపైలేషన్ ఎర్రర్ అవుతుంది.
  3. Varargs మెథడ్లను విపరీతంగా ఓవర్‌లోడ్ చేయడం: ఇది కాలర్ల వద్ద అంతుచిక్కని ambiguous method call ఎర్రర్‌లను తెచ్చిపెడుతుంది.
  4. లూపులలో ప్రతిసారీ Varargs ను పిలవడం: లూప్‌లో వేలాది సార్లు Varargs పిలిస్తే ప్రతిసారీ కొత్త తాత్కాలిక ఎరే హీప్‌లో ఏర్పడి GC పై భారం పడుతుంది. భారీ లూపులకు స్పష్టమైన ఎరే లేదా కలెక్షన్లను ముందే కేటాయించండి.

✨ ప్రొడక్షన్ గోల్డెన్ రూల్స్ (Golden Rules):

1. పనితీరు కోసం: తరచూ వాడే 1 లేదా 2 ఆర్గ్యుమెంట్ల కోసం స్పష్టమైన ఓవర్‌లోడెడ్ మెథడ్స్ రాసి, అదనపు ఆర్గ్యుమెంట్ల కోసమే Varargs వాడండి.
2. కనీస ఇన్‌పుట్ గ్యారెంటీ: Varargs మెథడ్‌కు కనీసం ఒక ఆర్గ్యుమెంట్ తప్పనిసరి చేయాలనుకుంటే foo(Type first, Type... rest) పద్ధతిని అనుసరించండి.
3. కంపైలర్ భద్రత: జెనరిక్ Varargs తో పనిచేసేటప్పుడు Heap Pollution హెచ్చరికలను నివారించడానికి @SafeVarargs అనోటేషన్ వాడండి.

🧠 మీ అవగాహనను పరీక్షించుకోండి (5 Interactive Quizzes):

ప్రశ్న 1: మెథడ్ ఓవర్‌లోడింగ్‌ను 'కంపైల్-టైమ్ పాలిమార్ఫిజం' అని ఎందుకు అంటారు?

సమాధానం: కంపైలేషన్ సమయంలోనే పారామీటర్ల రకాలు మరియు సంఖ్య ఆధారంగా ఏ నిర్దిష్ట మెథడ్‌ను పిలవాలో జావా కంపైలర్ ఖరారు చేస్తుంది (Static Binding) కాబట్టి.

ప్రశ్న 2: కేవలం రిటర్న్ టైప్ మాత్రమే వేరుగా ఉన్న రెండు మెథడ్లను ఒకే క్లాస్‌లో ఓవర్‌లోడ్ చేయవచ్చా?

సమాధానం: చేయలేము! పారామీటర్ల సంఖ్య, రకం లేదా క్రమంలో ఎటువంటి మార్పు లేకుండా కేవలం రిటర్న్ టైప్ మారిస్తే కంపైలేషన్ ఎర్రర్ వస్తుంది.

ప్రశ్న 3: Widening, Autoboxing మరియు Varargs లలో దేనికి అత్యధిక ప్రాధాన్యత ఉంటుంది?

సమాధానం: Widening (ప్రిమిటివ్ ప్రమోషన్) కి మొదటి ప్రాధాన్యత, ఆ తర్వాత Autoboxing, మరియు చివరిగా Varargs కి ప్రాధాన్యత లభిస్తుంది.

ప్రశ్న 4: ఒక మెథడ్ పారామీటర్ల లిస్ట్‌లో Varargs ఎక్కడ ఉండాలి?

సమాధానం: తప్పనిసరిగా చివరి పారామీటర్‌గా (Last Parameter) మాత్రమే ఉండాలి మరియు ఒక మెథడ్‌కు ఒక Varargs మాత్రమే అనుమతించబడుతుంది.

ప్రశ్న 5: 'void log(String... msgs)' మెథడ్‌కు ఎటువంటి ఆర్గ్యుమెంట్లు పంపకుండా 'log()' అని పిలిస్తే ఏమవుతుంది?

సమాధానం: ప్రోగ్రామ్ విజయవంతంగా రన్ అవుతుంది! JVM అంతర్గతంగా పొడవు 0 ఉన్న ఖాళీ ఎరేను (new String[0]) సృష్టించి పంపుతుంది.
