GraphQL — Apollo Federation & Subgraphs

1Simple Introduction

In API engineering, understanding Apollo Federation & Subgraphs is essential for building flexible, strongly-typed GraphQL APIs. GraphQL replaces multiple REST endpoints with a single endpoint and client-driven field selections.

3Why Apollo Federation & Subgraphs is Useful
💡 Practical Utility

4Resource & Schema Design

GraphQL Schema Type / Entity: Federation. GraphQL schemas use SDL (Schema Definition Language) to define explicit types, fields, and relationships.

5GraphQL Operation Type

Operation Type: POST. Specifies whether the operation reads data (Query), modifies state (Mutation), or streams real-time updates (Subscription).

10Server-Side Flow & Resolver Execution
GraphQL HTTP POST Request -> AST Parsing & Schema Validation -> Root Resolver Execution -> Nested Resolver Tree Walk -> DataLoader Batching -> JSON Data Payload Response
11Validation

GraphQL engine automatically validates incoming query strings against the target Schema definition before resolver execution. Unrecognized fields or incorrect scalar types trigger schema validation errors before database execution.

12Database Operation / Service Execution

Resolvers execute database operations or call underlying microservices using ORM queries (e.g. Prisma, TypeORM, Mongoose), utilizing DataLoader to batch parallel ID lookups into single SQL queries.

13Common Mistakes
⚠️ Anti-Patterns to Avoid
  • Causing N+1 query database bottlenecks by fetching nested relationships inside un-batched field resolvers.
  • Forgetting to secure introspection or query depth in production, exposing full schema definitions to public scanners.
  • Overusing custom scalars when built-in primitives or Input objects suffice.
  • Exposing sensitive database fields directly in GraphQL schemas without context authentication checks.
