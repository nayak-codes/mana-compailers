Git & GitHub — Rebasing Explained

🔀 Git & GitHub 🟢 Lesson 8 📅 2026
Rebasing is an alternative to merging that produces a cleaner, more linear project history. It has a reputation for being intimidating, but the core idea is simple once you see it visually: rebasing rewrites your branch as if it had started from a newer point in history.
1What Rebase Actually Does

Instead of creating a merge commit that ties two histories together, rebasing takes all the commits from your branch and "replays" them one by one on top of the latest commit from another branch:

git checkout feature-login
git rebase main

The end result looks as if you had started your feature branch from today's main, rather than from whenever you actually branched off — giving you a clean, straight-line history instead of a web of merge commits.

2Rebase vs Merge: When to Use Each

Use merge when you want an honest record of exactly when and how branches combined — ideal for shared, public branches. Use rebase to clean up your own local, not-yet-shared branch before merging it, making the eventual history easier for teammates to read.

3The Golden Rule of Rebasing

Never rebase a branch that other people are already using or have already pulled. Rebasing rewrites commit history — literally creates brand new commits with new hashes — which causes serious, confusing problems for anyone else who already has the old version of that branch.

⚠️ Common Mistake: Rebasing a Shared/Public Branch

This is the single most common way beginners cause real damage with Git. Rebasing a branch that teammates have already pulled rewrites its history under their feet, and their next git pull will produce a tangled mess of duplicate commits. Only rebase branches that exist solely on your own machine.

💻 Try It Yourself

On a local practice branch (never on a shared one), try rebasing onto main and observe how the log becomes a straight line instead of showing a merge commit.

git checkout feature-signup
git rebase main
git log --oneline --graph
