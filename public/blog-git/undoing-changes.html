Git & GitHub — Undoing Changes

🔀 Git & GitHub 🟢 Lesson 9 📅 2026
Everyone makes mistakes — a bad commit message, a file staged by accident, or code that simply doesn't work. Git gives you several different tools to undo changes, and choosing the right one depends on exactly how far back you need to go.
1Unstaging a File

If you staged a file with git add but changed your mind before committing:

git restore --staged filename.txt

This removes the file from the staging area but keeps your actual edits in the working directory — nothing is lost.

2Discarding Uncommitted Changes

To completely throw away edits to a file and go back to its last committed version:

git restore filename.txt

Use this carefully — unlike unstaging, this permanently deletes your uncommitted edits with no way to recover them.

3Undoing Commits: revert vs reset

These two commands are easily confused but behave very differently:

git revert <commit-hash>   # creates a NEW commit that undoes the old one — safe for shared history
git reset --hard <commit-hash>  # rewrites history, deleting commits entirely — only for local, unshared work

revert is almost always the safer choice on any branch other people might also be using, because it preserves history instead of erasing it.

⚠️ Common Mistake: Using git reset --hard Without Understanding It's Permanent

git reset --hard immediately and permanently discards all changes after the target commit — there is no undo, no recycle bin, no confirmation prompt. Before using --hard, double-check you truly don't need any of the work you're about to erase.

💻 Try It Yourself

Make a change to a file, stage it, then practice safely unstaging and restoring it back to its original state.

echo "test change" >> notes.txt
git add notes.txt
git restore --staged notes.txt
git restore notes.txt
