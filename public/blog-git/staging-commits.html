Git & GitHub — Staging & Committing Changes

🔀 Git & GitHub 🟢 Lesson 4 📅 2026
Git tracks changes in two distinct steps: first you choose which changes to include (staging), then you permanently record them (committing). Understanding this two-step process is the single most important concept for using Git confidently.
1The Working Directory, Staging Area, and Repository

Every file in a Git project exists in one of three places:

  • Working directory — the actual files you're editing right now
  • Staging area (also called the "index") — a holding area for changes you've marked as ready to be saved
  • Repository — the permanent, committed history

This separation exists so you can choose exactly which changes go into each commit, even if you've edited ten different files.

2Staging Changes with git add
git add index.html          # stage one specific file
git add .                    # stage every changed file in the current folder

Staging doesn't save anything permanently — it just marks files as "ready." You can still edit a staged file, but you'd need to run git add again to include the newest changes.

3Committing with a Meaningful Message
git commit -m "Add login form validation"

The -m flag lets you write your commit message inline. A good commit message is short, specific, and written in present tense — "Fix navbar alignment on mobile" is far more useful to future-you than "updated stuff."

⚠️ Common Mistake: Committing Without Staging Anything First

Running git commit -m "message" without first running git add will fail or commit nothing new, because nothing is staged yet. Beginners often forget this two-step requirement and wonder why their changes "aren't saving."

💻 Try It Yourself

Create a text file, stage it, and commit it with a clear message — the three commands every Git session relies on.

echo "Hello Git" > notes.txt
git add notes.txt
git commit -m "Add initial notes file"
