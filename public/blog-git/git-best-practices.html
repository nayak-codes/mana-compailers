Git & GitHub — Git Best Practices

🔀 Git & GitHub 🟢 Lesson 15 📅 2026
You now know the core Git commands and workflows — this final lesson collects the habits that separate clean, professional Git usage from messy, hard-to-follow project history.
1Writing Good Commit Messages

A commit message should complete the sentence "If applied, this commit will ___." "Fix login button not responding on mobile" is useful; "fix" or "updates" is not. Keep the first line under about 50 characters, and add more detail on following lines if the change needs further explanation.

2Commit Small, Commit Often

A single commit should represent one logical change — not "today's work" bundled into one giant blob. Small, focused commits are far easier to review, easier to revert individually if something breaks, and make git log genuinely useful as project documentation rather than noise.

3Use a .gitignore File

Certain files should never be committed: dependency folders like node_modules/, build output, environment files containing secrets, and OS-specific files like .DS_Store. Create a .gitignore file listing patterns to exclude:

node_modules/
.env
*.log
.DS_Store

Git will simply stop tracking anything matching these patterns, keeping your repository clean and preventing sensitive files like API keys from ever being accidentally pushed.

⚠️ Common Mistake: Committing Secrets or Dependency Folders

Accidentally committing an .env file with real API keys or a full node_modules/ folder is one of the most common real-world Git mistakes — and once pushed, that secret exists in your history forever unless you rewrite it, even if you delete the file in a later commit. Always set up .gitignore before your very first commit on a new project.

💻 Try It Yourself

Create a basic .gitignore file for a typical Node.js project and confirm Git respects it.

echo "node_modules/" >> .gitignore
echo ".env" >> .gitignore
git status   # ignored files should no longer appear as untracked
