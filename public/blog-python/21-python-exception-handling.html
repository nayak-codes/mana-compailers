ఎక్సెప్షన్ హ్యాండ్లింగ్ & కస్టమ్ ఎర్రర్స్

🌐 Modern Python 3.12+ 📖 Chapter 21 of 25 📁 Phase 05: OOP, ఎక్సెప్షన్స్ & ప్రాజెక్ట్ 🗓️ 2026 Edition
📌 Covered in this chapter: try-except-else-finally ఆర్కిటెక్చర్ · స్టాండర్డ్ ఎక్సెప్షన్స్ · raise కీవర్డ్ · కస్టమ్ ఎక్సెప్షన్ క్లాసెస్ నిర్మాణం (Domain Exceptions) · Syntax Errors vs Runtime Exceptions · try-except-else-finally Architecture · Exception Hierarchy · raise & Exception Chaining (raise from) · Custom Domain Exception Classes · FinTech Payment Gateway Resilient Engine
మీరు ఒక ఆన్‌లైన్ పేమెంట్ యాప్ లేదా ఫ్లైట్ బుకింగ్ పోర్టల్‌ను వాడుతున్నప్పుడు, సర్వర్‌లో ఇంటర్నెట్ కనెక్షన్ పోయినా లేదా వినియోగదారుడు తప్పుడు పిన్ నంబర్ నమోదు చేసినా — యాప్ మొత్తం క్రాష్ అయిపోయి ఎర్రటి కోడ్ స్క్రీన్ కనిపిస్తే మీకు ఎంత చిరాకు వస్తుంది? ఒక బిగినర్ రాసే కోడ్‌కు మరియు ఒక ప్రొఫెషనల్ సాఫ్ట్‌వేర్ ఇంజనీర్ రాసే ప్రొడక్షన్ కోడ్‌కు మధ్య ఉన్న అతిపెద్ద వ్యత్యాసం — ఎర్రర్లను ఎదుర్కొనే తట్టుకునే శక్తి (Fault Tolerance & Resilience)!

వాస్తవ ప్రపంచంలో ఊహించని సమస్యలు ఎప్పుడైనా రావచ్చు. సర్వర్ ఫైల్ డిలీట్ కావచ్చు, జీరోతో భాగహారం జరగవచ్చు, లేదా బ్యాంక్ సర్వర్ డౌన్ కావచ్చు. ఇటువంటి సంక్షోభ పరిస్థితులలో కూడా ప్రోగ్రామ్ కుప్పకూలిపోకుండా హుందాగా తట్టుకుని, యూజర్‌కు సరైన సమాచారం అందించి రక్షించే కవచమే ఎక్సెప్షన్ హ్యాండ్లింగ్ (Exception Handling)! ఈ అధ్యాయంలో మనం try-except-else-finally నిర్మాణం నుండి కస్టమ్ డొమైన్ ఎక్సెప్షన్ క్లాస్‌ల సృష్టి మరియు బ్యాంకింగ్ పేమెంట్ గేట్‌వే రిజిలియంట్ ఇంజిన్ వరకు సమగ్రంగా నేర్చుకుందాం!

1 ఎర్రర్ vs ఎక్సెప్షన్ అంటే ఏమిటి? & Traceback అనాటమీ

పైథాన్‌లో ప్రోగ్రామ్ ఆగిపోవడానికి రెండు ప్రధాన కారణాలు ఉంటాయి:

  • సింటాక్స్ ఎర్రర్స్ (Syntax Errors / Parsing Errors): పైథాన్ వ్యాకరణ నియమాలను ఉల్లంఘించినప్పుడు వస్తాయి (ఉదాహరణకు కాలన్ : మర్చిపోవడం లేదా బ్రాకెట్లు మూయకపోవడం). ఇవి కోడ్ రన్ అవ్వకముందే కంపైలర్ పట్టుకుంటుంది. వీటిని try-except ద్వారా ఆపలేము.
  • రన్‌టైమ్ ఎక్సెప్షన్స్ (Runtime Exceptions): సింటాక్స్ అంతా సరిగ్గానే ఉన్నప్పటికీ, ప్రోగ్రామ్ రన్ అవుతున్న సమయంలో ఎదురయ్యే అనూహ్య సమస్యలు (ఉదాహరణకు 10 / 0 జీరో డివిజన్, ఫైల్ లేకపోవడం, లేదా రాంగ్ కీ వెతకడం). వీటిని మనం ఎక్సెప్షన్ హ్యాండ్లింగ్ ద్వారా నియంత్రించి ప్రోగ్రామ్ క్రాష్ కాకుండా కాపాడవచ్చు!

పైథాన్ Traceback యొక్క అనాటమీ (ఎలా చదవాలి?):

Traceback (most recent call last):
  File "checkout.py", line 42, in process_payment
    discount = user_discounts[coupon_code] # 👈 ఎర్రర్ జరిగిన నిర్దిష్ట లైన్
KeyError: 'DIWALI2026' # 👈 [ఎక్సెప్షన్ రకం]: [ఎర్రర్ సందేశం]

ట్రేస్‌బ్యాక్‌ను ఎల్లప్పుడూ క్రింది నుండి పైకి (Bottom-Up) చదవాలి. చిట్టచివరి లైన్ ఏ రకమైన ఎర్రర్ వచ్చిందో స్పష్టంగా చెబుతుంది, దాని పై లైన్లు అది ఏ ఫంక్షన్ కాల్ ద్వారా అక్కడికి చేరుకుందో వివరిస్తాయి.

2 The try-except బ్లాక్ ఆర్కిటెక్చర్ & Anti-Patterns

పైథాన్‌లో ఎక్సెప్షన్లను పట్టుకోవడానికి try మరియు except బ్లాక్‌లను ఉపయోగిస్తాము:

try:
    # ప్రమాదం పొంచి ఉన్న కోడ్ (Risky Code)
    number = int(input("ఒక సంఖ్యను నమోదు చేయండి: "))
    result = 100 / number
except ValueError:
    print("దయచేసి సరైన పూర్ణాంక సంఖ్యను మాత్రమే ఇవ్వండి!")
except ZeroDivisionError:
    print("సున్నాతో భాగించడం అసాధ్యం!")
⚠️ The Bare Except Anti-Pattern:
ఎట్టి పరిస్థితుల్లోనూ ఎటువంటి పేరు పేర్కొనకుండా కేవలం except: లేదా except Exception: pass అని గుడ్డిగా రాయకండి! ఇది యూజర్ ప్రోగ్రామ్‌ను ఆపడానికి నొక్కే Ctrl+C (KeyboardInterrupt) మరియు మెమరీ ఎర్రర్లను కూడా సైలెంట్‌గా మింగేస్తుంది, దీనివల్ల ప్రొడక్షన్‌లో బగ్‌లు ఎక్కడున్నాయో కనిపెట్టడం అసాధ్యం అవుతుంది.

3 బహుళ ఎక్సెప్షన్లను హ్యాండిల్ చేయడం (Multiple & Grouped)

ఒకే try బ్లాక్‌కు వేర్వేరు సమస్యలకు వేర్వేరు except బ్లాక్‌లు రాయవచ్చు, లేదా ఒకే రకమైన చర్య కోసం బహుళ ఎక్సెప్షన్లను ఒక టుపుల్ రూపంలో గ్రూప్ చేయవచ్చు:

except (ValueError, TypeError, KeyError) as err:
    print(f"ఇన్‌పుట్ ప్రాసెసింగ్ ఎర్రర్: {err}")

4 The else బ్లాక్ యొక్క ప్రాముఖ్యత (No Exceptions Flow)

try బ్లాక్‌లో ఎటువంటి ఎర్రర్ రాని సందర్భంలో మాత్రమే ఎగ్జిక్యూట్ అవ్వాల్సిన కోడ్‌ను else బ్లాక్‌లో రాస్తాము.

చాలా మంది డెవలపర్లు ఈ కోడ్‌ను కూడా try లోపలే రాస్తుంటారు. కానీ try లో కేవలం ప్రమాదకరమైన లైన్‌ను మాత్రమే ఉంచి, మిగిలిన పనిని else లో ఉంచడం పరిశ్రమ ప్రామాణిక క్లీన్ కోడ్ పద్ధతి!

5 The finally బ్లాక్ — గ్యారెంటీడ్ క్లీనప్ (Guaranteed Cleanup)

try బ్లాక్ సక్సెస్ అయినా, లేదా ఎర్రర్ వచ్చి except బ్లాక్ రన్ అయినా, లేదా చివరకు ప్రోగ్రామ్ క్రాష్ అయ్యే పరిస్థితి వచ్చినా సరే — తప్పనిసరిగా 100% ఎగ్జిక్యూట్ అయ్యే ఏకైక బ్లాక్ finally!

  • రిసోర్స్ క్లీనప్: డేటాబేస్ కనెక్షన్లను క్లోజ్ చేయడానికి, నెట్‌వర్క్ సాకెట్లను విడుదల చేయడానికి, మరియు టెంపరరీ ఫైళ్లను డిలీట్ చేయడానికి finally సరైన ప్రదేశం.

6 ఎక్సెప్షన్లను విసరడం: raise కీవర్డ్

పైథాన్ మాత్రమే కాకుండా, మన వ్యాపార నిబంధనలు (Business Rules) ఉల్లంఘించబడినప్పుడు మన స్వంతంగా కూడా ఎక్సెప్షన్‌ను విసరవచ్చు. దీనికి raise కీవర్డ్‌ను ఉపయోగిస్తాము:

if withdraw_amount > account_balance:
    raise ValueError("ఖాతాలో సరిపడా నిల్వ లేదు!")

7 కోడ్ డెమో 1: లైవ్ బ్యాంకింగ్ ఫండ్ ట్రాన్స్‌ఫర్ with Full Suite

try-except-else-finally యొక్క పూర్తి సమగ్ర ప్రవర్తనను క్రింది కోడ్‌లో చూడండి:

01_banking_exception_suite.py 
# =====================================================================
# చాప్టర్ 21 డెమో 1: try - except - else - finally ఆర్కిటెక్చర్
# =====================================================================

def transfer_funds(sender_bal: float, amount: float):
    print(f"\n--- లావాదేవీ ప్రారంభం: మొత్తం ₹{amount:,.2f} ---")
    connection_open = True
    print("🔌 బ్యాంకింగ్ సెక్యూర్ గేట్‌వే కనెక్ట్ చేయబడింది.")

    try:
        if amount <= 0:
            raise ValueError("బదిలీ మొత్తం ₹0 కంటే ఎక్కువ ఉండాలి!")
        if amount > sender_bal:
            raise ArithmeticError("ఖాతాలో తగినంత నగదు నిల్వ లేదు!")

        new_balance = sender_bal - amount

    except ValueError as ve:
        print(f"❌ ఇన్‌పుట్ లోపం: {ve}")
    except ArithmeticError as ae:
        print(f"❌ బ్యాంకింగ్ నిల్వ లోపం: {ae}")
    else:
        # ఎర్రర్ రాకపోతేనే ఎగ్జిక్యూట్ అవుతుంది!
        print(f"✅ లావాదేవీ విజయవంతం! తాజా బ్యాలెన్స్: ₹{new_balance:,.2f}")
    finally:
        # ఎర్రర్ వచ్చినా రాకపోయినా ఖచ్చితంగా రన్ అవుతుంది!
        connection_open = False
        print("🔒 సెక్యూర్ గేట్‌వే కనెక్షన్ క్లోజ్ చేయబడింది (Cleaned up).")

# టెస్ట్ 1: విజయవంతమైన బదిలీ
transfer_funds(50000.0, 15000.0)

# టెస్ట్ 2: తగినంత నిల్వ లేని సందర్భం
transfer_funds(10000.0, 25000.0)

8 పైథాన్ స్టాండర్డ్ ఎక్సెప్షన్స్ హైరార్కీ (The Hierarchy)

పైథాన్‌లోని అన్ని ఎక్సెప్షన్లు ఆబ్జెక్ట్ ఓరియెంటెడ్ క్లాస్ రూపంలో ఉంటాయి. ఇవన్నీ ఒక నిర్దిష్టమైన వంశవృక్షాన్ని (Inheritance Hierarchy) కలిగి ఉంటాయి:

[Python Exception Class Hierarchy]
BaseException (అత్యున్నత మూల క్లాస్ - సాధారణంగా డైరెక్ట్‌గా క్యాచ్ చేయకూడదు)
  ├── SystemExit (sys.exit() ద్వారా వస్తుంది)
  ├── KeyboardInterrupt (Ctrl+C నొక్కినప్పుడు వస్తుంది)
  └── Exception (అన్ని సాధారణ అప్లికేషన్ ఎర్రర్లకు మూల క్లాస్) 🌟
        ├── ArithmeticError ──▶ ZeroDivisionError, OverflowError
        ├── LookupError ─────▶ IndexError, KeyError
        ├── ValueError
        ├── TypeError
        └── OSError ─────────▶ FileNotFoundError, PermissionError

అత్యంత తరచుగా ఎదురయ్యే కోర్ ఎక్సెప్షన్ల విశ్లేషణ:

  • ZeroDivisionError: ఏదైనా సంఖ్యను సున్నాతో భాగించడానికి ప్రయత్నించినప్పుడు వస్తుంది.
  • IndexError: లిస్ట్ లేదా టుపుల్ పరిధి దాటిన ఇండెక్స్‌ను (ఉదా: 3 ఎలిమెంట్లు ఉన్న లిస్ట్‌లో lst[10]) యాక్సెస్ చేయాలని చూస్తే వస్తుంది.
  • KeyError: డిక్షనరీలో ఉనికిలో లేని కీని బ్రాకెట్లతో (d['missing']) వెతికినప్పుడు వస్తుంది.
  • TypeError: అనుకూలం కాని డేటా రకాలపై ఆపరేషన్ చేసినప్పుడు (ఉదా: "హలో" + 5) వస్తుంది.
  • ValueError: సరైన డేటా రకమే అయినప్పటికీ విలువ చెల్లనప్పుడు (ఉదా: int("abc")) వస్తుంది.
  • AttributeError: ఒక ఆబ్జెక్ట్‌లో లేని మెథడ్ లేదా వేరియబుల్‌ను కాల్ చేయాలని చూసినప్పుడు వస్తుంది.

9 ఎక్సెప్షన్ చైనింగ్ (raise ... from)

పైథాన్ 3 లో ఒక ఎర్రర్‌ను హ్యాండిల్ చేస్తూ మరొక ఉన్నత స్థాయి ఎర్రర్‌ను విసిరినప్పుడు, అసలైన మూల కారణం (Root Cause) మరుగున పడకుండా కాపాడే అద్భుతమైన ఫీచరే raise ... from original_error!

ఎంటర్‌ప్రైజ్ మైక్రోసర్వీసెస్ మరియు RESTful APIలలో సాధారణ ValueError సరిపోదు. API రెస్పాన్స్‌లో సరైన HTTP స్టేటస్ కోడ్ (ఉదా: 400 Bad Request, 401 Unauthorized, 404 Not Found, 409 Conflict) మరియు ఎర్రర్ పేలోడ్ పంపడానికి ఒక చక్కని కస్టమ్ ఎక్సెప్షన్ హైరార్కీని నిర్మిస్తాము:

# కస్టమ్ ఎక్సెప్షన్ క్లాసెస్
class OutOfStockError(Exception):
    """ఉత్పత్తి నిల్వ లేనప్పుడు వచ్చే ఎర్రర్."""
    pass

class InsufficientBalanceError(Exception):
    """యూజర్ వాలెట్‌లో తగినంత నగదు లేనప్పుడు వచ్చే ఎర్రర్."""
    pass

def checkout_order(item_name: str, requested_qty: int, available_stock: int, total_price: float, wallet_bal: float):
    if requested_qty > available_stock:
        raise OutOfStockError(f"క్షమించండి! '{item_name}' స్టాక్ కేవలం {available_stock} మాత్రమే ఉంది.")
    if total_price > wallet_bal:
        shortfall = total_price - wallet_bal
        raise InsufficientBalanceError(f"వాలెట్‌లో ₹{shortfall:,.2f} తక్కువగా ఉంది!")

    print(f"🎉 ఆర్డర్ కన్ఫర్మ్ అయింది! వస్తువు: {item_name} (పరిమాణం: {requested_qty})")

# టెస్టింగ్
try:
    checkout_order("స్మార్ట్‌ఫోన్", requested_qty=3, available_stock=1, total_price=45000, wallet_bal=50000)
except OutOfStockError as ose:
    print(f"🚨 ఇన్వెంటరీ హెచ్చరిక: {ose}")
except InsufficientBalanceError as ibe:
    print(f"🚨 పేమెంట్ హెచ్చరిక: {ibe}")

12 కామన్ బిగినర్స్ మిస్టేక్స్ & ప్రొడక్షన్ బెస్ట్ ప్రాక్టీసెస్: EAFP vs LBYL

పైథాన్‌లో ఎక్సెప్షన్ హ్యాండ్లింగ్ కేవలం ఎర్రర్లను నివారించడానికి మాత్రమే కాదు; ప్రోగ్రామింగ్ శైలిని (Design Philosophy) తీర్చిదిద్దే అత్యంత ప్రముఖమైన సిద్ధాంతం. ఇతర భాషల్లో (C, Java) సాధారణంగా LBYL (Look Before You Leap) శైలిని ఉపయోగిస్తారు, కానీ పైథాన్‌లో ఆధునిక నిపుణులు EAFP (Easier to Ask for Forgiveness than Permission) శైలికి ప్రాధాన్యత ఇస్తారు:

EAFP vs LBYL తులనాత్మక పోలిక:

  • LBYL (Look Before You Leap): ఏదైనా ఆపరేషన్ చేసే ముందు, అనేక if కండిషన్లను ఉంచి అది సాధ్యమేనా అని పరిశీలించడం. ఉదాహరణకు డిక్షనరీలో కీ ఉందా లేదా అని if key in dict: ద్వారా వెతకడం, లేదా ఫైల్ ఉందా అని if os.path.exists(filepath): అని చూడటం. దీని లోపం: మల్టీ-థ్రెడింగ్ లేదా డిస్ట్రిబ్యూటెడ్ ఎన్విరాన్‌మెంట్‌లో "Time-of-Check to Time-of-Use" (TOCTOU) రేస్ కండిషన్ రావడం వల్ల మీరు చెక్ చేసిన మరుక్షణమే మరొక ప్రాసెస్ ఆ ఫైల్‌ను తొలగించవచ్చు.
  • EAFP (Easier to Ask for Forgiveness than Permission): ఆపరేషన్ విజయవంతం అవుతుందనే సానుకూల అంచనాతో నేరుగా ప్రయత్నించి (try), అరుదుగా పొరపాటు జరిగితే క్షమాపణ కోరుతూ ఎక్సెప్షన్‌ను క్యాచ్ చేయడం (except KeyError). ఇది వేగవంతమైనది మరియు అదనపు అనవసరపు లుకప్ ఖర్చులను నివారిస్తుంది.
# 1. LBYL పద్ధతి (సాంప్రదాయ):
if "user_token" in session_cache:
    token = session_cache["user_token"]
else:
    token = None

# 2. EAFP పైథానిక్ పద్ధతి (సిఫార్సు చేయబడినది):
try:
    token = session_cache["user_token"]
except KeyError:
    token = None
  • The Silent Failure Pitfall: except: pass అని రాయడం వల్ల ఎర్రర్లు కప్పిపుచ్చబడి భవిష్యత్తులో డేటాబేస్ కరప్ట్ అయ్యే ప్రమాదం ఉంది. ఎర్రర్ వస్తే కనీసం లాగ్ (Log) చేయండి.
  • తప్పుడు ఆర్డర్‌లో ఎక్సెప్షన్స్ క్యాచ్ చేయడం: పేరెంట్ క్లాస్‌ను (Exception) మొదట రాసి, దాని క్రింద చైల్డ్ క్లాస్‌ను (ValueError) రాస్తే — పేరెంట్ క్లాసే అన్నింటినీ ముందే క్యాచ్ చేసేస్తుంది! ఎల్లప్పుడూ స్పెసిఫిక్ ఎక్సెప్షన్లు పైభాగంలో, జెనరిక్ క్లాస్ చివరిలో ఉండాలి.
  • finally బ్లాక్‌లో return రాయడం: finally లో return రాస్తే, try లేదా except లో వచ్చిన ఒరిజినల్ రిటర్న్ వాల్యూ లేదా ఎక్సెప్షన్ పూర్తిగా అణచివేయబడుతుంది!
  • స్పెసిఫిక్ ఎక్సెప్షన్లు మాత్రమే క్యాచ్ చేయండి: సాధారణ except Exception: రాయడం కంటే except (KeyError, ValueError) as err: వంటి నిర్దిష్టమైన క్లాసులను క్యాచ్ చేయడం ద్వారా కోడ్ క్లీన్‌గా మరియు డీబగ్ చేయడానికి అనువుగా ఉంటుంది.

13 రియల్-వరల్డ్ ప్రాజెక్ట్: "Enterprise FinTech Payment Gateway & Resilient Engine"

            except (CardExpiredError, InsufficientFundsError, ValueError) as client_err:
                # క్లయింట్ వైపు తప్పులకు రీట్రై చేయకూడదు! తక్షణమే ఆపాలి.
                print(f"  ❌ మార్చలేని లోపం: {client_err}")
                raise client_err

            finally:
                print(f"  📝 లావాదేవీ ఆడిట్ లాగ్ నమోదు చేయబడింది (Attempt #{attempt}).")

# లైవ్ టెస్టింగ్
processor = FinTechPaymentProcessor(merchant_id="MERC-HYD-9901")

# టెస్ట్ 1: నెట్‌వర్క్ రీట్రై ద్వారా సక్సెస్ అయ్యే లావాదేవీ
try:
    res1 = processor.execute_charge("TXN-1001", card_token="CARD-TIMEOUT", amount=3500.0)
    print(f"\n🎉 లావాదేవీ విజయవంతం! ఆథరైజేషన్ కోడ్: {res1['auth_code']}")
except Exception as e:
    print(f"\n🚨 లావాదేవీ శాశ్వతంగా విఫలమైంది: {e}")

# టెస్ట్ 2: కార్డు గడువు ముగిసిన కేసు (నో రీట్రై)
try:
    res2 = processor.execute_charge("TXN-1002", card_token="CARD-EXPIRED", amount=1200.0)
except Exception as e:
    print(f"\n🚨 లావాదేవీ తిరస్కరించబడింది: {e}")

★ ఈ అధ్యాయంపై ప్రాక్టీస్ క్విజ్ (Knowledge Check)

1. try బ్లాక్‌లో ఎర్రర్ రాకపోతే ఏ బ్లాక్ ఎగ్జిక్యూట్ అవుతుంది?
సమాధానం: try బ్లాక్‌లో ఎటువంటి ఎక్సెప్షన్ రానప్పుడు else బ్లాక్ ఎగ్జిక్యూట్ అవుతుంది. ఆ తర్వాత finally బ్లాక్ రన్ అవుతుంది.
2. except: pass అని రాయడం ఎందుకు తీవ్రమైన తప్పు (Anti-pattern)?
సమాధానం: ఇది ఏ రకమైన ఎర్రర్ వచ్చిందో చూడకుండా అన్నింటినీ మరుగున పరుస్తుంది (Silent Failure). సిస్టమ్ ఎర్రర్లను, యూజర్ నొక్కే Ctrl+C ఇంటరప్ట్‌లను కూడా ఆపేస్తుంది. దీనివల్ల బగ్‌లను కనుగొనడం అసాధ్యం అవుతుంది.
3. కస్టమ్ ఎక్సెప్షన్ క్లాస్‌ను ఎలా తయారు చేయాలి?
సమాధానం: పైథాన్ అంతర్నిర్మిత Exception క్లాస్‌ను ఇన్‌హెరిట్ చేయడం ద్వారా: class InvalidAgeError(Exception): pass.
4. raise ... from err సింటాక్స్ యొక్క ప్రయోజనం ఏమిటి?
సమాధానం: దీనిని Exception Chaining అంటారు. ఒక కొత్త ఎర్రర్‌ను విసురుతున్నప్పుడు, అసలైన మూల కారణమైన పాత ఎర్రర్‌ను కోల్పోకుండా ట్రేస్‌బ్యాక్‌లో రెండింటినీ చూపిస్తుంది.
5. finally బ్లాక్‌లో return స్టేట్‌మెంట్ రాయకూడదు ఎందుకు?
సమాధానం: finally లో return రాస్తే, try లేదా except లో వచ్చిన ఒరిజినల్ రిటర్న్ వాల్యూ లేదా రేజ్ అయిన ఎక్సెప్షన్ పూర్తిగా అణచివేయబడి రద్దు అవుతుంది.
